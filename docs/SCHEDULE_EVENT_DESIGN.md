# 日程、事件量级与状态归属设计

> 状态：**讨论记录，未实现。**
> 关联文档：[主动消息的话题连续性](PROACTIVE_TOPIC_DESIGN.md)

## 问题

同一个"事件"，对人的日程影响可能差几个数量级：

| 事件 | 合理反应 |
| --- | --- |
| 外面发洪水 | 立刻停止当前活动，改地点，今晚剩下的安排全部作废 |
| 有人敲门递了点吃的 | 几乎不影响安排，最多变成"边吃边打游戏" |

当前实现只有"改"和"不改"两档：模型一旦决定改，就被要求输出一整套剩余日程，
于是小事件也会引发大改写。缺少的是**影响半径**这个概念。

## 现状

### 日程结构

```json
"life": {
  "status": "在书房看书",
  "plan": [
    {"start": "19:00", "end": "21:00", "activity": "打游戏", "place": "客厅"}
  ]
}
```

- 地点 `place` **只存在于日程项里**，没有独立的"当前地点"字段。
- `status` 由当前日程段推导：`activity（place）`。

### 回写对日程的影响

```python
started = 已开始的条目        # 永不改动
future  = 未开始的条目
每项新安排：删除时间重叠的 future 项，再插入
```

结构上不是整体覆盖，但实际近似覆盖，原因是：

1. 回写提示词只给模型看**未来 2 条**（`life_summary` 的 `upcoming[:2]`）。
2. 却要求模型输出**完整剩余日程**。

模型看不到原日程，只能重编一份，时间区间重叠后把原来的替换掉。

## 设计：三层影响半径

| 层 | 改什么 | 例子 |
| --- | --- | --- |
| 当前时刻覆盖 | 只改"现在在做什么"，`plan` 不动 | 递吃的 → 状态变「边吃边打游戏」，半小时后回落 |
| 未来窗口 | 未来 1–3 小时的条目 | 朋友叫下楼 → 只挪动接下来两段 |
| 整天重写 | 剩余日程整体重建 | 洪水避难 → 今晚全部作废 |

原则：**不是让模型自由决定改多少，而是让它先声明量级，由代码限制允许的改动范围。**

### 量级判定

模型在回写时先给 `impact`，判据要互斥：

| 级别 | 判据 | 例子 |
| --- | --- | --- |
| `none` | 不影响安排 | 闲聊、问候 |
| `minor` | 只影响此刻，不动地点和安全 | 递吃的、喝水、被叫一声 |
| `moderate` | 改变未来几小时 | 临时被叫走、朋友来访、取快递 |
| `major` | 涉及安全 / 地点迁移 / 健康 / 取消约定 | 洪水、生病、家里出事 |

### 代码侧的范围校验

| 级别 | 允许的改动 |
| --- | --- |
| `none` | `plan` 一律不动，只改 mood/status/log |
| `minor` | 只能写当前时刻覆盖，**禁止**碰 `plan` |
| `moderate` | 只能改未来 3 小时内的条目 |
| `major` | 允许重写剩余日程 |

如果模型声明的级别和实际改动不匹配（`minor` 却改了晚上），
**拒绝越界部分**并记一条 `plan_scope_clamped`，让越权行为在审计里可见。

### 当前时刻覆盖

```json
"life": {
  "override": {"text": "边吃边打游戏", "until": 1763200000, "location": "客厅"}
}
```

- `advance_state` 优先渲染 `override`，过期自动回落到日程段
- 面板显示为「当前活动（临时）」
- 成本最低、效果最直观，对应"边吃边打游戏"

## 状态与地点归属（当前）

这是讨论中发现的问题：说要"更新状态和地点"，但这些数据现在记在谁身上？

| 数据 | 角色 | 对话对象 | 备注 |
| --- | --- | --- | --- |
| 心情 / 精力 | ✅ `life.mood` / `life.energy` | ❌ | |
| 当前状态 | ✅ `life.status`（派生） | ✅ `user.last_text`（原话） | 角色是描述，用户是原文 |
| 是否在睡 | ✅ `life.sleeping`（派生） | ✅ `user.sleeping`（关键词判定） | |
| 当前地点 | ⚠️ 只在 `plan[].place` | ⚠️ 只在 `user.away` 原话 | **两者都没有独立地点字段** |
| 日程 | ✅ `life.plan` | ❌ | |
| 事件记录 | ✅ `life.log` | ❌ | |

### 结论

1. **角色的状态是完整的**，但**地点是隐式的**——只作为日程项的属性存在。
   一旦事件要求"改地点但不改日程"（比如避难路上），就没有地方可写。
2. **对话对象只有睡眠/外出两个粗状态**，地点只是原话文本，无法参与判断。
3. **一人格只记录一个对话对象**：`persona_targets` 是一人格对一个会话，
   `observe_inbound` 只取 `message_str`，不取发送者。因此群聊绑定时，
   `user` 记录的是"这个群"，不区分群成员。

### 建议字段

```json
"life": {
  "location": "客厅",
  "location_source": "plan|event",
  "override": {"text": "", "until": 0, "location": ""},
  "event": {
    "id": "evt-1",
    "impact": "major",
    "text": "外面发洪水了",
    "applied_at": 0,
    "plan_before": [],
    "status": "active"
  }
},
"user": {
  "user_id": "",
  "place": "",
  "place_updated_at": 0
}
```

- `life.location` 由当前日程段的 `place` 派生，`major` 事件可显式覆盖
- `life.event` 记录**当前生效的事件**，`plan_before` 是改动前的日程快照
- `user.user_id` 现在只记录，不参与判断；为以后按发送者拆分预留

## 事件不是一次性的

`impact` 是**事件状态**，不是对某条消息的标签。人会误判严重程度，后续对话可能推翻它：

```
用户：外面好像发洪水了
角色：！（impact=major，重写今晚日程，保存 plan_before）
用户：虚惊一场，楼下只是水管爆了
模型：impact 修正为 minor，revert=true
代码：恢复 plan_before，清掉 override
```

所以必须满足两条：

1. 事件带状态（`active` / `revised` / `reverted`），可被后续对话改写。
2. 进入 `major` 前保存 `plan_before`，否则"虚惊一场"时已经无从恢复。

降级不需要保留历史，升级才需要；`plan_before` 只在存在 active 事件时保留一份。

## 小概率"反应过度"归谁

| 判断 | 归属 | 原因 |
| --- | --- | --- |
| 这件事有多严重 | **模型** | 语义判断，代码做不了 |
| 这次要不要夸张一点 | **代码** | 概率行为需要可关、可审计；模型对"随机"没有校准能力 |

实现：代码先掷一次 `overreact_probability`（默认 0），命中后告诉模型
"这次可以比实际严重一点"，并在合并时把级别**最多上调一级**，且**永不自动升到 `major`**——
`major` 意味着现实行动（避难、取消约定），不能由随机数触发。

审计里记录 `plan_impact_escalated`，方便事后判断是不是太频繁。

## 落地顺序

| 阶段 | 内容 | 改动量 | 状态 |
| --- | --- | --- | --- |
| 0 | `observe_inbound` 记录 `user.user_id`（为群聊拆分预留） | 1 行 | ⬜ |
| 1 | 回写只输出变化，并把完整未来日程喂给模型 | ~30 行 | ⬜ |
| 2 | `life.override` 当前时刻覆盖 + `minor` 判定 | ~60 行 | ⬜ |
| 3 | `impact` 声明 + 代码侧范围校验（`plan_scope_clamped`） | ~80 行 | ⬜ |
| 4 | 事件状态 + `plan_before` + 修正/回滚（`revert`） | ~70 行 | ⬜ |
| 5 | `life.location` 独立字段 + `major` 联动地点/状态 | ~30 行 | ⬜ |
| 6 | `user.place`（可选，只在明确说出时记录） | ~20 行 | ⬜ |
| 7 | `overreact_probability` 概率上调（默认 0，关闭） | ~30 行 | ⬜ |
| 8 | 环境事件源（天气预警等外部输入） | 独立工作 | ⬜ |

阶段 8 说明：洪水这类信息目前只能从对话里得知。真正的环境触发需要接天气预警源
（原插件用和风天气预警，本插件没有）。架构上只要把事件定义为
`{kind, text, impact}`，以后接任何来源都不必改核心逻辑。

## 已决事项

| 问题 | 结论 |
| --- | --- |
| 群聊按发送者拆分 | 现在不做，只记录 `user.user_id` 预留；需要时把 `user` 改成 `users[sender_id]` |
| `impact` 是否一次性 | 不是。事件有状态，可被后续对话修正，`major` 需保存 `plan_before` 以便回滚 |
| 小事件偶发升级 | 严重程度由模型判断，是否"夸张"由代码掷概率决定；默认关闭，最多升一级，禁止自动到 `major` |

## 群聊拆分的代价

现在 `user` 是会话级字段。绑群聊时，不同成员的状态会互相覆盖
（`sleeping`、`away`、`last_text` 都会串）。所以：

- **近期建议只绑私聊房间**，避免状态串号。
- 拆分时的改造点集中在：`observe_inbound`（取 `sender_id`）、`user` 读取处、
  `proactive_prompt` 的“对方情况”、面板的「对方」一行。
- 数据迁移只需把旧的 `user` 包成 `users[user_id or "default"]`，是一次小型迁移。
